# Expérience 1 : TodoMVC (JavaScript vanilla)

## Cible et autorisation

- Cible : `1Marc/modern-todomvc-vanillajs`, une liste de tâches d'environ 200 lignes.
- Autorisation : code public. Licence Creative Commons Attribution 4.0 (TasteJS) : citer l'auteur si du code est réutilisé.

## Objectif

Mesurer si REA comprend correctement le comportement d'une petite application web, puis reconstruire notre propre version et la comparer à l'original.

## Méthode

1. **Analyse à l'aveugle.** L'agent analyse l'application avec REA sans lire les fichiers source à la main. Règle d'honneur : il ne les ouvre qu'à l'étape 4.
2. **Rapport REA.** Il liste le comportement trouvé (ajouter, cocher, modifier, supprimer, filtrer, compteur, sauvegarde), avec une preuve pour chaque point.
3. **Reconstruction.** Il écrit sa propre version dans `reconstruction/todomvc/`, sans copier le code de l'original.
4. **Comparaison.** Il ouvre ensuite le vrai code et note les écarts : comportements manqués, erreurs, points justes.

## Résultats

### Comportements trouvés par REA (étape 2)

_Rédigé avant toute ouverture manuelle des fichiers source._

#### Conditions de l'analyse

- Cible clonée hors du dépôt, dans le dossier temporaire de la session (`scratchpad/cible/modern-todomvc-vanillajs`), commit `58e4669bd959f1b8f8c63a8b2ab6f55173f6104d` (12 mars 2024). Empreinte REA du dossier : `sha256:a90a8af1…1fbd8`.
- Seule action hors REA sur la cible : lister les fichiers et leur taille (`find` + `wc -c`), sans les lire.
- Application servie en local (`python3 -m http.server`, port 8731) et ouverte dans Chromium headless lancé par moi avec un port CDP local (9333). REA s'y connecte en mode `connect`.
- Le mode `launch` de `capture_browser_scenario` a échoué : Chromium refuse de démarrer en root sans `--no-sandbox`, et la variable `REA_BROWSER_NO_SANDBOX` ne peut pas être passée au serveur MCP déjà démarré. D'où le Chromium lancé à la main.
- Quatre scénarios navigateur rejoués (19 + 17 + 10 + 7 étapes), avec DOM, arbre d'accessibilité, URL et empreintes du localStorage capturés après chaque étape. La sortie console et les erreurs de page étaient demandées : aucun événement retenu (REA marque cette section comme incomplète en mode `connect`, donc l'absence d'erreur n'est pas prouvée).

Identifiants de preuve REA (session MCP) : analyse statique `ev_0598a09d…`, inspection de page `ev_2050f34d…`, scénario 1 `ev_60e0fad1…`, scénario 2 `ev_af947e29…`, scénario 3 `ev_4f79b37b…`, scénario 4 `ev_bbe3e72a…`.

#### Structure (analyse statique, `analyze_javascript_application`)

- 3 modules ES : `js/app.js` (140 lignes), `js/store.js` (71 lignes), `js/helpers.js` (14 lignes). `index.html` ne charge que `js/app.js` en `type="module"` ; les deux autres sont importés. Aucune dépendance d'exécution, aucun appel réseau (`fetch`, WebSocket) détecté.
- `store.js` exporte une classe `TodoStore` (l. 1-71). Elle appelle `window.localStorage.getItem` (l. 27) et `window.localStorage.setItem` (l. 30-33).
- `helpers.js` exporte quatre fonctions : `getURLHash` (l. 1), `delegate` (l. 3-7), `insertHTML` (l. 9), `replaceHTML` (l. 11-14). Les noms suggèrent un routage par le hash, une délégation d'événements et un rendu par chaînes HTML.
- Limite : le graphe sémantique garde 484 inconnues. `trace_javascript_semantics` sur l'appel `setItem` n'a rien donné de plus que sa position.

#### Ce que REA n'a pas permis d'établir à ce stade

- La manière dont les événements sont branchés (délégation sur la liste ? sur `document` ?) : `delegate` existe, mais je n'ai pas lancé `inspect_web_event_listeners` sur chaque élément.
- L'état de la propriété `checked` de `#toggle-all` (le DOM sérialisé ne montre que l'attribut, jamais posé).
- Le texte exact placé dans le champ `.edit` à l'ouverture et le focus après édition.
- Ce qui se passe si le localStorage contient autre chose qu'un tableau valide.
- Si l'écriture du stockage se fait aussi sur des actions sans effet (par exemple Échap).

### Ce qui a échoué ou reste incertain

- **Lancement du navigateur par REA** : `capture_browser_scenario` en mode `launch` a échoué (Chromium refuse root sans `--no-sandbox`). Contournement : Chromium lancé à la main avec un port CDP local, puis mode `connect`. Une variable `REA_BROWSER_NO_SANDBOX=true` dans la config MCP réglerait ce point pour les prochaines fois.
- **Schémas d'entrée compacts** : le serveur MCP n'expose qu'un schéma réduit (« compact input schema profile »). Les champs `capture`, `actions` et `view` n'y sont pas détaillés. Il a fallu des essais-erreurs, la doc REA (`search_guidance`) et la lecture du schéma Zod dans le paquet `rea-agents` installé (`dist/cli-runtime/browserScenarioValues-*.js`) pour trouver `after_each_step`, `at_end`, `click_count`, etc.
- **CLI REA bloqué** : un `npx rea-agents --help` a été refusé par le classifieur de permissions de la session. Seuls les outils MCP ont servi.
- **Traçage sémantique** : `trace_javascript_semantics` (depuis l'appel `setItem`) ne renvoie que le nœud de départ, sans flux de données exploitable. Le format du stockage a été établi par une méthode indirecte : hacher des hypothèses et les comparer aux empreintes SHA-256 relevées par REA.
- **Console et erreurs de page** : demandées, mais section « events » incomplète en mode `connect`. Aucune erreur vue, mais rien ne prouve qu'il n'y en avait pas.
- **Couverture des scénarios** : deux onglets, clavier seul (Tab/Espace), hash inconnu et localStorage corrompu n'ont pas été testés. Ce sont justement les écarts trouvés à l'étape 4.

## Bilan

- **Fiabilité de REA sur cette cible : bonne sur tout ce qui se voit dans le navigateur.** Les 22 points de l'étape 2 sont justes, dont un seul en partie (édition vide : la ligne reste en mode édition). Les manques portent sur ce qui ne se voit pas dans un seul onglet piloté à la souris : synchronisation entre onglets, focus conservé au rendu, robustesse au stockage corrompu, architecture par événement `save`. L'analyse statique seule a donné une bonne carte (modules, exports, accès au stockage, lignes) mais presque rien sur le comportement. C'est la combinaison avec les scénarios navigateur qui a fait le travail.
- **Outils REA réellement utilisés :** `analyze_javascript_application` (carte statique) ; `inspect_analysis_view` (lecture des preuves : faits JS, DOM, stockage, accessibilité étape par étape) ; `inspect_web_page` (état initial, scripts chargés, stockage) ; `capture_browser_scenario` en mode `connect` (4 scénarios, 53 étapes) ; `trace_javascript_semantics` (peu utile ici) ; `search_guidance` et `read_guidance_section` (format des actions). Non utilisés : `analyze_web_bundle`, `inspect_web_event_listeners`, `observe_web_execution`, `trace_application_feature`.
- **Reconstruction :** `reconstruction/todomvc/` (modèle pur + rendu DOM, environ 250 lignes JS). 7 tests unitaires et un parcours Playwright des 22 points passent. Elle diffère de l'original sur les points manqués (pas de synchro entre onglets, pas de restauration du focus) et sur des choix assumés (édition vide qui ferme le champ, stockage tolérant, identifiants sans doublon, clé de stockage distincte).
- **Suite à donner :**
  1. Ajouter `REA_BROWSER_NO_SANDBOX=true` à l'entrée `rea` de `.mcp.json` pour que REA lance lui-même le navigateur dans ce conteneur.
  2. Ajouter au protocole des scénarios « deux onglets », « clavier seul » et « stockage corrompu », et un passage de `inspect_web_event_listeners` sur les éléments clés (champ, liste, `window`) pour attraper les écouteurs comme `storage`.
  3. Mettre à jour la reconstruction avec la synchro entre onglets et la restauration du focus, en les rattachant à de nouvelles observations REA, pas au code lu.
  4. Prochaine cible : une application minifiée ou empaquetée, où l'analyse statique ne pourra pas s'appuyer sur des noms lisibles (`analyze_web_bundle`).
